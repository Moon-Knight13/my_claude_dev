A multi-environment operator hub with safety built in.

A framework for running AI-assisted security operations and software development from a single Claude session. Work is mode-isolated and every change passes the same security gates before it merges.

For anyone

Why it exists

Two ideas do most of the work. You don't need to read code to get them.

Safe by default

The environment is locked down — the network can only reach an approved list, and secrets never touch the repo. Guardrails are on before the first line is written.

Humans stay in control

Every task is a tracked card and every change is a reviewed pull request. Nothing merges until the automated checks agree.

For engineers

The seven moving parts

Each is a self-contained piece of the platform. Seven operational modes — from platform-ops to red-team to homelab — activate different subsets of these parts.

Devcontainer.devcontainer/
A reproducible dev environment with a deny-by-default firewall — egress is allowlisted, tooling is pre-installed, Claude auth is a mounted volume.
Remote dev boxesscripts/local/ · scripts/host/
A laptop bootstrap wires up SSH, identity and Remote-SSH; an on-box provisioner brings a shared box to a known-good state and refuses to record success it did not verify.
BMAD workflow/bmad
Structured planning in six stages, Discovery through Security & Release, so features are scoped before they're built.
Kanban board/next-issue · /run-epic
A per-repo GitHub Project. Agents claim cards collision-free; a Route field makes the human/Claude/local decision visible on every card.
CI security gates.github/workflows/
gitleaks secret scanning, semgrep SAST (incl. MITRE ATLAS AI/ML rules), Trivy container scanning, and every scripts/tests suite (gates, guards, orchestrator) against local mocks — all enforced, not advisory.
MCP serversmcp-servers/ · .claude/settings.json
15+ MCP servers for targeting intel, C2 control, vulnerability scanning, technique reference, and knowledge management — each mode activates only the servers it needs. Range-facing servers reach spokes through an SSE proxy.
Technique scoringscripts/technique-scoring.py
Aggregates technique outcomes across engagements into composite scores for orchestrator grounding — ranking attack techniques by empirical success rate, recency, and stealth so the orchestrator picks what actually works.

On a remote box · live

The safety harness, in action

When Claude works on a shared dev box, these controls sit between the agent and the box and turn the risky actions into a human decision — or refuse them outright — while you watch. Built backwards from four things a developer worries an agent might do. Defense-in-depth and human-in-the-loop, deliberately not a sandbox: the shared-sudo box offers no OS isolation, so this stops the accidental and misread-instruction cases and puts a human in the loop for the dangerous ones — it does not contain a determined adversary.

Every agent tool call runs the gate first

~/.claude/hooks/pretooluse-ctp.sh → scripts/lib/guard-stack.sh
worry ① leak PII/IP
PII/IP path guard. A tool Read/Write or Bash command touching an owner-listed Org-data path is denied — its contents never reach the transcript. Hooks cannot redact tool output, so the read is refused, not sanitised. Opt-in via CTP_PII_PATHS.
deny
worry ② commit secrets
Commit guard. Every commit — human or agent, any repo — is scanned for secrets and PII. Warn + log, never blocks: an intentional commit is never stopped, a real leak is impossible to miss and logged (rule/file/line, never the value) to rotate fast.
warn
worry ③ destructive act
Destructive-action gate. rm -rf, dropdb, DROP/TRUNCATE, terraform destroy, kubectl delete, docker prune — the human confirms before it runs. No human present ⇒ it fails closed to a deny. Model-agnostic: one classifier lib any executor routes through.
ask
destructive git
Destructive-git gate. git push --force, reset --hard, clean -f, branch -D, checkout --force — the human confirms first (fails closed with no human). Reads the real command word, so a commit message that says "reset --hard" is not flagged.
ask
worry ④ web connection
Egress. Covered on the box by the org's restricted network — new outbound hosts are already gated at the edge. A hook-level visibility layer is planned on top.
org net
build tooling
Bridge. The agent cannot drive the deploy wrapper or docker directly — bare access is denied; a permitted verb raises a confirm bound to that exact command; a refused verb is denied.
ask / deny
credentials
Secret-read deny + killswitch. Credential files (vault, ~/.ssh keys, .env, history) are unreadable by any tool; and once the last session ends, credentials left on the shared account are shredded so the next connector authenticates as themselves.
deny / shred

The hook runs outside the agent's command, so the agent cannot disable it; if its guard stack is missing it fails closed and denies every call. Its limits come from a gitignored on-box config, never the agent's environment. The checks above are one composed policy in scripts/lib/guard-stack.sh, not logic living in the hook: the hook parses the tool call and renders a verdict, the stack decides. That matters because there are now two enforcement points: this hook, and the local-model executor below, which does not go through Claude and so does not inherit the hook. Sharing one library is what stops the two drifting apart. Every control is demonstrable — feed the hook a tool call and read its verdict, or ask Claude to do the risky thing and watch the prompt. Full walkthrough: docs/SAFETY_HARNESS.md. check-day0.sh reports each control's posture honestly (present · warn-only · bypassable · box-only).

Roadmap · v3 vision

Next: multi-environment operator hub

The current architecture serves one environment (a dedicated cyber range). v3 generalizes the framework to support independent operational domains — CTF challenges, penetration tests, bug bounties, software development, and homelab infrastructure — each with its own modes, knowledge bases, and model failover.

New operational modes

planned · .claude/modes/

dev

General software development. No offensive tools, full coding toolchain. The default for non-security work.

ctf

CTF platform challenges (HTB, THM, Proving Grounds). Flag-oriented, no OPSEC requirements. Per-challenge threads.

pentest

Client penetration testing. SOW-scoped, formal reporting, alternative C2 integration. Per-engagement threads.

bounty

Bug bounty programs. Program policy as scope definition, web-focused tooling, no C2 needed.

Existing modes (base, platform-ops, green-dev, red-team, red-dev, purple, homelab) remain unchanged. Each new mode follows the same structure: system prompt, settings, and tool policy.

T3-native routing

planned · replaces hook-injected mode switching

Why: hook-injected mode rules degrade in long sessions (context bleed, routing ambiguity). T3 threads give structural context isolation, persistent mode sessions, and a clean audit trail. Security improves: hooks are project-scoped and fire on all threads, including delegate children. The .active-mode shared-state gap is solved by project-per-mode-group. Partially operational: T3 Code is already the orchestration surface — the master agent delegates implementation to threads and stays router-only. project-routes.yaml maps modes to projects with mismatch detection in the mode-inject hook.

Model failover chain

planned · cost-aware
Tier 0 · Claude MAX
Primary. Opus 4.6, full capability. Subscription, already paid. Used for all complex reasoning, architecture, and security work.
cloud · subscription
Tier 1 · Homelab vLLM
First failover. Abliterated open-weight model on controlled infrastructure. Zero marginal cost. Also handles prompts that hit content policy blocks.
self-hosted · zero cost
Tier 2 · Cloud GPU
Insurance. Serverless vLLM on cloud GPU provider. Same model as homelab. Pay-per-second when homelab is down.
cloud · pay-per-use
Tier 3 · Local Ollama
Emergency. On-laptop, degraded capability. Zero cost. Always available as last resort.
local · zero cost

Failover triggers: 5xx, timeout, rate limit, content policy block. Content policy blocks skip directly to Tier 1 (abliterated model handles legitimate security research prompts). The failover harness is a provider-agnostic CLI (OpenCode) with MCP support.

Vault-per-mode knowledge bases

planned · Obsidian + semantic search MCP

Domain isolation

Each mode gets its own Obsidian vault. CTF notes stay out of pentest searches. A shared reference vault (MITRE, cheatsheets) is available to all modes.

Semantic search

A new vault-search MCP backed by local embeddings (nomic-embed-text on homelab) gives agents context-aware retrieval beyond keyword matching.

Accumulating advantage

Knowledge bases grow with use. Every engagement, challenge, and research session feeds the vault. The model is swappable; the accumulated experience is not.

Build sequence: structure vaults, deploy embedding model (homelab), build vault-search-mcp (platform-ops), populate organically during work. Tier 1 search (obsidian-mcp keyword) works today.

What makes this a framework, not a weapon

portfolio positioning
no operational data
No credentials, targets, findings, or engagement-specific configuration in the repository. Operational data lives in vaults and environment profiles outside the repo.
by design
infra-coupled skills
Offensive skills require range connectivity and C2 server access to function. Without the infrastructure, they are inert documentation.
by design
safety harness
Fail-closed, tested, documented, and demonstrable. Published alongside offensive capability — not hidden from it.
documented

Less directly weaponizable than open-source C2 frameworks and attack path analysis tools that are widely published and used in the industry.
