Claude Secure Template

A guarded workshop where AI does the work and nothing ships unchecked.

A production-ready starting point for building software with Claude. Work comes in, gets routed to whoever should do it — a person, Claude, or a cheaper local model — and every change passes the same security gates before it merges.

For anyone

Why it exists

Three ideas do most of the work. You don't need to read code to get them.

Safe by default

The environment is locked down — the network can only reach an approved list, and secrets never touch the repo. Guardrails are on before the first line is written.

Cheap work goes local

Low-risk tasks are handed to a free model running on your own machine. Claude is spent only where its judgment is worth the cost.

Humans stay in control

Every task is a tracked card and every change is a reviewed pull request. Nothing merges until the automated checks agree.

For engineers

The six moving parts

Each is a self-contained piece of the template. Together they turn a blank repo into a governed, AI-assisted delivery pipeline.

Devcontainer.devcontainer/
A reproducible dev environment with a deny-by-default firewall — egress is allowlisted, tooling is pre-installed, Claude auth is a mounted volume.
Remote dev boxesscripts/local/ · scripts/host/
A laptop bootstrap wires up SSH, identity and Remote-SSH; an on-box provisioner brings a shared box to a known-good state and refuses to record success it did not verify.
AI routingscripts/route-model.sh
Classifies each task and sends it local vs Claude by risk. Hard triggers — auth, networking, broad refactors — always escalate to Claude.
BMAD workflow/bmad
Structured planning in six stages, Discovery through Security & Release, so features are scoped before they're built.
Kanban board/next-issue · /run-epic
A per-repo GitHub Project. Agents claim cards collision-free; a Route field makes the human/Claude/local decision visible on every card.
CI security gates.github/workflows/
gitleaks secret scanning, semgrep SAST (incl. MITRE ATLAS AI/ML rules), Trivy container scanning, and every scripts/tests suite (gates, guards, orchestrator) against local mocks — all enforced, not advisory.

A task is classified by type and risk; any hard trigger — auth, networking, 8+ files — always escalates to Claude. The same decision shows up as the Route field on the board card.

The local endpoint differs by surface. In the devcontainer the model runs on the host; on a remote box it runs on the developer's own machine and arrives over a reverse SSH tunnel only if the developer opts in (the tunnel is unauthenticated to other users of the shared box). When nothing answers, routing falls back to Claude and the work still completes — local is an optimisation, never a dependency.

On a remote box · live

The safety harness, in action

When Claude works on a shared dev box, these controls sit between the agent and the box and turn the risky actions into a human decision — or refuse them outright — while you watch. Built backwards from four things a developer worries an agent might do. Defense-in-depth and human-in-the-loop, deliberately not a sandbox: the shared-sudo box offers no OS isolation, so this stops the accidental and misread-instruction cases and puts a human in the loop for the dangerous ones — it does not contain a determined adversary.

Every agent tool call runs the gate first

~/.claude/hooks/pretooluse-ctp.sh → scripts/lib/guard-stack.sh
worry ① leak PII/IP
PII/IP path guard. A tool Read/Write or Bash command touching an owner-listed Org-data path is denied — its contents never reach the transcript. Hooks cannot redact tool output, so the read is refused, not sanitised. Opt-in via CTP_PII_PATHS.
deny
worry ② commit secrets
Commit guard. Every commit — human or agent, any repo — is scanned for secrets and PII. Warn + log, never blocks: an intentional commit is never stopped, a real leak is impossible to miss and logged (rule/file/line, never the value) to rotate fast.
warn
worry ③ destructive act
Destructive-action gate. rm -rf, dropdb, DROP/TRUNCATE, terraform destroy, kubectl delete, docker prune — the human confirms before it runs. No human present ⇒ it fails closed to a deny. Model-agnostic: one classifier lib any executor routes through.
ask
destructive git
Destructive-git gate. git push --force, reset --hard, clean -f, branch -D, checkout --force — the human confirms first (fails closed with no human). Reads the real command word, so a commit message that says "reset --hard" is not flagged.
ask
worry ④ web connection
Egress. Covered on the box by the org's restricted network — new outbound hosts are already gated at the edge. A hook-level visibility layer is planned on top.
org net
build tooling
Bridge. The agent cannot drive the deploy wrapper or docker directly — bare access is denied; a permitted verb raises a confirm bound to that exact command; a refused verb is denied.
ask / deny
credentials
Secret-read deny + killswitch. Credential files (vault, ~/.ssh keys, .env, history) are unreadable by any tool; and once the last session ends, credentials left on the shared account are shredded so the next connector authenticates as themselves.
deny / shred

The hook runs outside the agent's command, so the agent cannot disable it; if its guard stack is missing it fails closed and denies every call. Its limits come from a gitignored on-box config, never the agent's environment. The checks above are one composed policy in scripts/lib/guard-stack.sh, not logic living in the hook: the hook parses the tool call and renders a verdict, the stack decides. That matters because there are now two enforcement points: this hook, and the local-model executor below, which does not go through Claude and so does not inherit the hook. Sharing one library is what stops the two drifting apart. Every control is demonstrable — feed the hook a tool call and read its verdict, or ask Claude to do the risky thing and watch the prompt. Full walkthrough: docs/SAFETY_HARNESS.md. check-day0.sh reports each control's posture honestly (present · warn-only · bypassable · box-only).

Enforcement point #2 — the local executor

scripts/orchestrator/execute-local.sh → scripts/lib/guard-stack.sh
why it exists
Sensitive work that needs tools. A task too sensitive to send to a cloud model used to have two options: describe a fix it could not make, or go somewhere it should not. The executor runs the file and shell work on the box instead, driven by a local model.
local
same rulebook
One policy, two doors. The executor bypasses Claude, so it bypasses the hook — and therefore calls the same guard stack itself. One deliberate difference: it may read the owner's Org-data paths, because doing that without egress is its entire purpose. Credentials stay denied on both doors.
deny / ask
fixed vocabulary
read_file · write_file · list_dir · run_command. Declared before the run and not extensible: a model asking for a fifth tool gets told the list is fixed. Every one is classified the same way — a write_file at an SSH key is refused exactly as a shell command naming it would be.
closed set
human in the loop
Confirm at the terminal. An ask verdict stops and waits, the same prompt the hook raises. Both stdin and stdout must be a TTY, so piping the run counts as nobody being there — and with nobody there, the answer is no.
ask
injection containment
Read text is data, never instruction. Tool output arrives in a labelled channel and never joins the system prompt; every call is judged on what it does, never on why; a step budget caps any sequence injected text could start. Bounds injection — honestly, does not eliminate it.
structural
log hygiene
Opaque handles, never paths. The run log records which tool ran, what the guard said and the exit code — with targets as handles meaningful only inside one run. A log Claude can read stays an index of nothing.
handles
what crosses back
A declared interface, never the artifact. The human at the terminal gets the raw answer; a cloud-bound caller gets a contract — name, invocation, inputs, outputs, exit codes. See the disclosure boundary below.
contract

Opt in per run with orchestrate.sh --tools; without it the local path stays reasoning-only, so an existing run never silently gains a shell. The tier decision happens before dispatch and is not revisited here — the executor is a second way to do local work, never a second way onto the cloud. Its system prompt follows the same pattern as the classifier's: a generic default in the repo, the owner's real policy on the box in ~/.config/orchestrator/, which is hidden from Claude's tools by default. Full walkthrough: docs/ORCHESTRATOR.md.

The disclosure boundary — what Claude is allowed to know

scripts/lib/contract.sh
declare, don't scrub
Only named fields are copied. A filter fails open — whatever the rewrite misses, crosses. A contract fails closed: a note or rationale the local model added is not scrubbed, it is never copied. Undeclared content was never in the message, so there is nothing to miss.
positive
no paths, ever
A path is disclosure on its own. A customer directory gives away org structure, client identity and codenames even when file contents never move. Artifacts are referenced by a random opaque handle; a slash anywhere in a declared value rejects the contract outright.
deny
the word list, twice
Before and after the sanitiser. The owner's private terms are matched by code on the draft and again on the exact text about to cross — an LLM rewrite can introduce words as well as remove them. It is the only check here with no judgement in it.
deny
sanitiser blocks here
Failure is not passthrough on this path. The contract came straight out of sensitive material, so a timed-out sanitiser blocks. The owner may override at the terminal, once, after reading the raw text — logged, never a setting, and it never skips the word list.
block
owner approves each one
Every contract, not just the first. Written by an AI from sensitive material, where one variable name can carry a codename. The owner sees the final text exactly as it would cross. Deliberately strict and deliberately revisable — loosening later is easy, tightening later is not.
ask
stated limit
No unattended co-operation. Approval needs a terminal, so Claude and the local model cannot work together with nobody watching. That is a property of the design, not a gap — and the first thing that changes if the local model earns more trust.
honest

This is the mechanism that lets a cloud model coordinate work it is never allowed to see: Claude writes the playbook, the pipeline, the caller — knowing the name, the arguments and the exit codes of a script whose contents, logic and originating prompt stay on the box. The handle-to-path map is itself a list of internal paths, so it lives in ~/.config/orchestrator/ with everything else Claude's tools cannot read, and is never resolved for a cloud-bound caller. Full walkthrough: docs/ORCHESTRATOR.md.

Roadmap · design only

Next: the SP1a trust core (planned)

Most of this does not exist yet; the parts that have landed are listed at the end of this section. SP1a is the agreed design for doing sensitive work with a local model while Claude handles the heavy non-sensitive work — with sensitive material kept out of Claude's reach by separation first and a fail-closed gate as the safety net.

One trusted hub, one untrusted container per session

planned · docs/SP1A_ARCHITECTURE.md

The container's only ways out are three sockets the hub creates for that one session. Everything Claude is about to see goes through the gate; every git-host write leaves from the hub; web traffic reaches only allowlisted domains. The diagram shows the planned design.

What it will do

planned
separation
Sensitive work never enters the container. Only workspaces the operator marks mountable go in, and only after a full scan, history included. Everything else stays on the hub with the local model.
lane 1 / lane 2
the gate
Two layers, allow or block. A term list and a local classifier check prompts, expansions, tool inputs and tool results. Never rewrites. Any fault is a block.
fail closed
opaque verdicts
Claude sees only a ref. The reason goes to the operator as a hub notification, so the model cannot learn which rule matched.
ref only
breach
Sensitive content found inside means stop. The session is latched, frozen and cut off, and the workspace quarantined until the operator reviews it — with a login token rotation offered.
latch · cut
push from the hub
The container cannot push. The hub checks every new object, path and message, then pushes to an allowlisted repo. Issue and PR text goes through a relay.
hub only
fallbacks
Only by declaration. A floor-only session when the classifier is down, or an UNPROTECTED container that says so at start. The gate never picks either itself.
visible

Honest limit: until a later outbound gateway, anything in the container could still be sent to any account on an allowlisted service — accepted only because the container holds nothing sensitive. Full design, threat model and decision index: docs/SP1A_ARCHITECTURE.md in the repository.
